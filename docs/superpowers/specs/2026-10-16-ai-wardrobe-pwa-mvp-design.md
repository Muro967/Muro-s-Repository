# AI Wardrobe PWA MVP 设计规格

日期：2026-10-16  
状态：已与 Muro 完成口头确认，等待书面规格复核

## 1. 产品定义

AI Wardrobe 是一款安装到手机桌面使用的渐进式 Web App。它帮助用户记录自己已有的衣物，从穿搭灵感中学习个人偏好，并结合天气、场景和现有衣橱生成可穿的搭配。产品的核心不是衣物库存，而是“按用户喜欢的风格，只用用户已经拥有的衣服推荐搭配”。

第一阶段先供 Muro 自己试用，但账号、数据和调用额度从第一天起按多用户隔离。产品界面使用简体中文，品牌名和少量装饰标题保留英文。

品牌名为 **AI Wardrobe**，标语为 **穿你所有，爱你所穿**。

## 2. MVP 成功标准

第一版只有在以下整条链路真实可用时才算完成：

1. 用户可以通过邀请码创建账号并登录，将 PWA 添加到手机桌面。
2. 用户可以建立多个衣柜和分区，录入、编辑、移动和删除衣物。
3. 录入照片后立即出现预览，上传、抠图、取色和 AI 识别异步完成，失败步骤可单独重试。
4. 用户可以添加灵感图，得到可编辑的风格画像和风格说明书。
5. 用户可以从灵感图发起复刻，也可以按天气和场景生成三套日常搭配。
6. 搭配中的衣物与配饰全部来自用户当前可用的衣橱，不得包含虚构、已处置或规则排除的单品。
7. 用户可以替换单品、收藏、喜欢或不喜欢搭配、填写不喜欢原因，并确认当天穿着。
8. 穿着记录会改变衣物的最后穿着时间，并正确驱动闲置、观察和处置状态。
9. 用户换设备登录后仍能找回数据，也能导出完整备份。

## 3. MVP 范围

### 3.1 账号与首次使用

- 公开注册关闭。用户必须使用有效邀请码创建邮箱和密码账号。
- 邀请码可设置最大使用次数和失效时间；用尽、失效或已撤销的邀请码不能注册。
- 登录后首次进入引导用户填写昵称、常用城市、发长和发质，并创建第一个衣柜。
- 每条业务数据必须属于一个用户，任何查询和修改都必须验证当前用户身份。
- 第一版不做短信验证码、第三方登录和公开注册；以后添加登录方式时不迁移业务数据。

### 3.2 衣橱、衣柜和分区

- 支持多个衣柜；衣柜可新增、改名、排序和删除。
- 每个衣柜支持挂衣区、层板、抽屉和鞋层四种分区；分区可新增、改名、排序和删除。
- 删除仍有衣物的分区前，用户必须选择这些衣物的新位置。
- 衣柜页提供分类和风格两种浏览方式，并显示分类文件夹、衣物数量及三列衣物网格。
- 衣物可在不同衣柜和分区之间移动。
- 基础搜索支持名称、分类、颜色和衣柜位置；多条件高级筛选不进入 MVP。
- 衣物删除后进入 30 天回收期。回收期内可恢复；期满后永久删除对应图片和记录。

### 3.3 衣物录入

- 支持调用相机或从相册选择图片。
- 选择图片后立即显示本地预览，不等待上传或 AI。
- 后台处理顺序为：压缩与方向校正、上传原图、抠图、取色、生成缩略图、视觉识别。
- 界面分别显示“正在上传”“正在抠图”“正在识别”“需要重试”和“已完成”，不得用一个无限加载状态覆盖所有步骤。
- AI 识别字段包括分类、子分类、颜色名、季节、厚度、材质、版型、长度、正式程度和风格标签。
- 用户可在 AI 完成前保存草稿，也可修改所有 AI 生成字段。
- 用户必须选择衣柜和分区后才能将衣物正式设为“在用”。

### 3.4 灵感与风格说明书

- 灵感图支持拍照、相册多选和粘贴剪贴板图片。
- 不提供小红书、Instagram 或其他第三方平台链接导入。
- 每张灵感图由 AI 提取一至三个风格标签、主要色系、廓形、关键单品和组合关系，结果均可编辑。
- 五张有效灵感图之后生成风格画像；不足五张时显示还需添加的数量，不生成伪精确百分比。
- 风格说明书包含偏爱色系、偏爱廓形、常用组合、正式程度倾向、喜欢示例和“不喜欢”硬规则。
- 用户可以直接编辑风格说明书。“不喜欢”规则在搭配筛选阶段作为硬约束。
- 灵感详情页提供“用我的衣服复刻”操作。结果说明哪些部分相似，以及衣橱中缺少什么；缺少的单品只作差异说明，不生成购买推荐。

### 3.5 搭配与反馈

- 场景固定为通勤、休闲、运动、派对、正式和度假。
- 服务端先按状态、品类、季节、厚度、天气、场景和“不喜欢”规则筛选候选单品。
- AI 基于候选单品的编号和文字描述生成六至八套候选，不直接自由创造单品。
- 服务端验证每个编号确实属于当前用户、状态可用且未被规则排除，再对候选进行完整性和风格匹配评分，最终返回三套。
- 每套至少包含上装与下装，或一件连体/裙装，并包含鞋；外套、包和配饰按需要添加。
- 配饰只能来自用户衣橱，没有合适配饰时允许留空。
- 每套显示场景、风格、参考灵感、推荐理由和发型建议。发型建议依据用户设置的发长、发质，并附短发替代建议。
- 用户可替换同类单品、换一批、收藏、喜欢或不喜欢。不喜欢原因至少包括“太正式”“颜色不搭”“不像我”，并允许补充文字。
- 用户点击“今天穿这套”后创建当天穿着记录并更新涉及衣物的穿着信息。当天记录可修改；过去七天允许补记。

### 3.6 闲置、观察和处置

- 默认超过 90 天未穿的在用衣物进入闲置列表；该天数可在设置中修改。
- 新入库前 30 天不计闲置。明显非当季的衣物在当前季节不计闲置。
- 用户可将闲置衣物放入观察中，默认观察期为 30 天；该天数可修改。
- 观察期内产生穿着记录时，衣物自动退出观察并恢复在用状态。
- 观察期到期后提醒用户处理，但不得自动处置。
- 处置方式包括二手卖出、送给朋友、捐赠、旧衣回收、改造和丢弃。
- 二手卖出可记录售价和平台；送人可记录接收人；所有方式记录处置日期和可选备注。
- 已处置衣物不参与搭配和闲置率计算，但保留历史穿着与处置信息。
- 闲置率为“当前闲置衣物数 ÷ 当前在用衣物数”。处置率为“已处置衣物数 ÷（已处置衣物数 + 当前闲置衣物数）”。

### 3.7 我的、同步和导出

- “我的”显示单品、搭配、灵感数量和基础衣橱分布。
- 设置包含衣柜与分区、闲置与观察天数、常用城市、发长发质、云端同步状态、AI 用量、隐私与数据。
- 导出内容包括结构化数据文件、衣物原图和抠图、灵感图、穿着照片及一份可读清单，打包为 ZIP。
- 月度报告不进入 MVP。
- 每日提醒和 Web Push 不作为 MVP 验收条件，可在核心链路稳定后增加。

## 4. 视觉与交互基准

实现必须参考已存入项目的 `docs/references/ai-wardrobe-sketch/AI-Wardrobe-sketch-spec.md`、`docs/references/ai-wardrobe-sketch/ai-wardrobe-sketch.html` 和 `docs/references/ai-wardrobe-sketch/screens/` 中的十八张截图。它们是视觉基准，不是技术实现约束；其中 SwiftUI、SwiftData、CloudKit、Vision、iCloud、TestFlight 和 Keychain 等原生 iOS 描述不适用于本项目。

保留以下视觉语言：

- 背景 `#F2EEE8`，卡片 `#FBF9F6`，主文字 `#3E3A36`，次文字 `#857D75`。
- 主色 `#6E7B6A`，辅色使用 `#9CAA97`、`#C9A8A1`、`#EBDCD7`、`#A4B4BE`、`#DCE3E7`、`#B8977F` 和 `#E8E0D4`。
- 英文装饰标题使用 Cormorant Garamond；中文标题优先 Noto Serif SC；正文优先 Noto Sans SC，并提供系统字体回退。
- 大圆角卡片、轻阴影、低对比层级、分类文件夹、三列衣物网格、横向 Look 卡片和四项悬浮胶囊 Tab。
- AI 自动填写字段使用雾蓝色 AI 角标；所有加载、失败和空状态沿用同一设计语言。

PWA 适配规则：

- 主要设计宽度为 390 CSS 像素，但必须支持 320 至 480 像素手机宽度，不允许依赖固定截图尺寸。
- 使用安全区域变量避开刘海和底部手势区。
- 页面内容必须能被浏览器字体缩放，不用图片承载正文。
- 所有交互目标至少 44×44 CSS 像素；键盘焦点可见；尊重减少动态效果设置。
- “iCloud 同步”统一改为“云端同步”；模拟状态栏不进入正式页面。
- 草图中的“抠图 1.2 秒”改为实际耗时或处理中状态，不显示虚构速度。

## 5. 技术设计

### 5.1 总体结构

采用 Next.js、React 和 TypeScript 构建模块化全栈 PWA。浏览器负责界面、拍照选图、图片预处理、离线缓存和同步状态；服务端负责身份验证、数据权限、对象存储、AI 调用、调用额度和后台任务。

应用先以一个可容器化部署的服务运行。第一版不拆微服务，不引入 Redis；后台任务使用 PostgreSQL 任务表、租约和有限次数重试。任务量超过单实例可承受范围后再迁移到专用队列。

### 5.2 数据与文件

PostgreSQL 是正式业务数据源。对象存储保存原图、压缩图、抠图、缩略图、灵感图和穿着照片。浏览器 IndexedDB 保存最近内容、待上传文件和离线操作队列，不作为唯一数据源。

主要实体为：

- `User`、`InviteCode`、`Session`
- `Wardrobe`、`Zone`、`Category`、`Item`、`ItemAsset`
- `Inspiration`、`StyleProfile`、`StyleRule`
- `Outfit`、`OutfitItem`、`OutfitFeedback`、`WearLog`
- `DisposalRecord`、`ProcessingJob`、`ExportJob`、`UserSettings`

衣物的最近穿着日和穿着次数从有效穿着记录计算或由事务内派生缓存维护；任何修改穿着记录的操作都必须同时更新相关派生数据。季节、场景和风格使用代码内稳定编号，显示名称可以独立修改。

### 5.3 AI 与规则引擎

服务端提供可替换的 AI Provider 接口，首个实现使用通义千问兼容 API。长期 API Key 只保存在服务端密钥配置中，不返回浏览器、不写入数据库普通字段、不进入日志。

视觉识别和文本生成都要求结构化 JSON 响应，并经过运行时模式校验。格式失败时只自动重试一次；再次失败则保存任务错误并允许用户重试。不得用无法校验的自然语言直接修改业务数据。

搭配由确定性规则和 AI 共同完成。规则负责候选范围、硬性限制和最终编号验证；AI 负责组合、风格匹配评分和自然语言理由。AI 无权绕过衣物状态、所属用户和风格禁忌。

### 5.4 登录与数据隔离

第一版使用邀请码加邮箱密码。密码只保存强密码哈希。会话使用安全、仅 HTTP、同站 Cookie。所有服务端数据访问都必须带当前用户条件；对象存储下载使用短时签名地址。

邀请码包含哈希后的码值、最大使用次数、当前使用次数、失效时间和撤销时间。注册过程在一个事务内验证并消耗邀请码，防止并发重复使用。

### 5.5 PWA 与离线行为

应用提供 Web App Manifest、图标、启动参数和 Service Worker。静态界面与最近使用的数据可离线打开；登录、图片处理、AI 识别、搭配生成和最终同步需要网络。

离线修改写入带唯一操作编号的本地队列。恢复网络后按创建顺序同步，服务端使用操作编号保证重复提交不会产生重复记录。第一版冲突策略为最后一次明确保存获胜，并在界面显示同步时间和冲突提示。

## 6. 隐私、安全与数据生命周期

- 衣物图和灵感图可发送给 AI 完成识别；穿搭人物照片默认不发送给 AI。
- AI 请求使用完成任务所需的压缩图和最少文字字段，不发送密码、邀请码、邮箱或对象存储长期地址。
- 日志不得记录 API Key、密码、完整邀请码、图片二进制或用户私密备注。
- 删除衣物先软删除 30 天；永久删除时清理派生图片和不再被其他记录引用的对象。
- 已处置不等于删除。已处置衣物保留历史记录，但从搭配候选中排除。
- 用户可以导出自己的数据。删除账号需要再次验证密码，并明确告知数据永久删除结果；该操作不在普通页面提供快捷入口。

## 7. 错误处理

- 图片处理的每一步独立记录状态、尝试次数和错误代码。重试只从失败步骤继续。
- 网络错误显示可执行的下一步，如“保留在手机，联网后继续上传”，不显示笼统的“发生错误”。
- AI 暂时不可用时，衣物仍可手动录入和编辑；搭配页说明暂时不能生成，而不是阻塞整个应用。
- 搭配候选不足时，明确说明缺少的必要品类，并提供返回衣橱的入口，不虚构补位单品。
- 数据库、对象存储和图片处理的跨资源操作使用可恢复状态，不向用户显示已经成功但实际未保存的数据。
- 同一用户在两台设备修改相同记录时，最后一次明确保存获胜，并显示最新同步时间。

## 8. 测试策略

- 领域单元测试覆盖邀请码消耗、数据隔离、衣物状态、闲置计算、观察期、处置率、搭配候选过滤、编号校验和反馈记录。
- API 集成测试使用临时数据库和对象存储替身，覆盖注册、登录、上传完成、任务重试、穿着确认和导出。
- 浏览器端组件测试覆盖四个 Tab、录入状态、表单编辑、分区移动、闲置处置弹层和离线队列提示。
- 端到端测试覆盖“邀请码注册 → 创建衣柜和分区 → 添加衣物 → 添加灵感 → 生成搭配 → 确认穿着 → 查看闲置变化 → 完成处置”。
- PWA 检查覆盖 Manifest、Service Worker、离线启动页、图标、安全区域和可安装性。
- 视觉回归以用户提供的截图为基准，重点检查颜色、字体、圆角、卡片间距、底部 Tab 和 390 像素宽度下的布局。
- 移动端人工验收至少覆盖一台当前 iPhone Safari 和一台 Android Chrome；首个内部版本可以先完成 iPhone Safari 验收。

## 9. 实施分解

本文件是 MVP 总设计。为控制风险，不把全部功能塞进一个开发计划；以下每个阶段分别编写实施计划、完成测试和验收，再进入下一阶段：

1. PWA 外壳、设计系统、邀请码账号、云端数据和对象存储基础。
2. 衣柜、分区、衣物录入、图片处理和基础搜索。
3. 灵感、风格画像、风格说明书和灵感复刻。
4. 搭配规则、AI 生成、替换、反馈、收藏和穿着记录。
5. 闲置、观察、处置、基础统计、同步状态和完整导出。
6. 移动端兼容、可访问性、性能、视觉回归和部署验收。

每一阶段都必须有可运行页面、自动化测试和真实数据路径，不以只有静态界面或只有接口作为完成标准。

## 10. 明确暂缓

以下功能不属于 MVP：月度报告、复杂组合搜索、每日 Web Push 提醒、短信验证码、第三方登录、公开注册、会员订阅、支付、后台运营面板、购买推荐、小红书或 Instagram 导入、社交分享、多人共同管理同一衣橱。
