# AI Wardrobe 第三阶段：灵感、风格说明书与灵感复刻设计规格

## 1. 阶段目标

本阶段把现有的手动衣柜扩展为可使用的灵感与风格系统。用户可以保存穿搭灵感图，维护每张图片的风格信息，在五张有效灵感图后形成可编辑的个人风格说明书，并从任意灵感图发起“用我的衣服复刻”。复刻只能使用当前账号衣柜中真实存在且状态为“在用”的衣物。

本阶段不要求用户先申请 AI API Key。系统必须同时支持规则预览和真实 AI 两种运行方式：没有 API Key 时，用户仍可完成图片保存、手动标注、风格聚合和基于衣物资料的规则复刻；配置通义千问兼容 API 后，系统才执行真实图片分析。任何界面都不得把规则结果或固定样例冒充 AI 识图结果。

## 2. 范围与完成标准

本阶段包含以下可运行能力：

- 从相册选择、相机拍摄或剪贴板粘贴 JPEG、PNG、WebP 灵感图；第一版继续明确说明不支持 HEIC。
- 选择图片后立即显示本地预览，图片上传和记录保存分别显示状态。
- 两列灵感墙、灵感详情、编辑、软删除与恢复失败提示。
- 每张灵感的名称、一至三个风格标签、主要色系、廓形、关键单品、组合关系和个人备注。
- 未配置 AI 时允许用户手动填写全部字段，并显示“手动整理”或“规则预览”；配置 AI 后显示真实的分析状态和 AI 角标。
- 五张有效灵感图后形成可编辑的风格说明书；不足五张时只显示还差几张，不显示百分比画像。
- 风格说明书包含偏爱色系、偏爱廓形、常用组合、正式程度倾向、喜欢示例和“不喜欢”硬规则。
- 从灵感详情发起复刻，得到一套只包含用户当前可用衣物的结果、相似点和缺失点。
- 规则预览与真实 AI 共用相同的业务校验；AI 返回的衣物编号必须再次由服务器验证。
- 页面、接口、数据库迁移、自动化测试、移动端端到端流程和阶段验证文档全部完成。

本阶段明确不包含每日天气搭配、场景生成三套搭配、换一批、单品替换、搭配反馈、收藏、穿着确认、穿着日志、衣物 AI 识别、背景抠除、购买建议和第三方平台链接导入。这些能力保留给后续搭配阶段或独立阶段。

## 3. 用户体验

### 3.1 灵感墙

灵感 Tab 沿用用户认可的米白、灰绿、豆沙色视觉语言。顶部显示英文装饰标题、灵感数量、添加入口和风格说明书入口；主体使用两列自适应瀑布流，卡片展示私密图片、名称和一至三个标签。页面支持 320 至 480 CSS 像素宽度，主要验收宽度为 390 CSS 像素。

空状态保留“还没有灵感图”的温和提示，并提供明确的添加按钮。已有灵感时，不再显示静态示例或虚构统计。添加入口提供“从相册选择”“拍照”和“粘贴图片”；剪贴板没有图片或浏览器不允许读取时，说明原因并保留相册入口。

不足五张有效灵感时，页面显示“再添加 N 张，就能形成你的风格说明书”。有效灵感指图片已完成上传、记录未删除，且至少拥有一个风格标签或一个主要色系；仍在上传、只有空白字段或已删除的记录不计入门槛。

### 3.2 灵感添加与详情

选图后立即显示本地预览。用户可以先保存图片记录，再等待真实 AI 分析或手动整理字段。上传失败时保留当前页面中的本地预览和已填写内容，允许只重试上传；记录保存失败时不得显示为已经保存。

详情页展示原图、来源状态、分析状态和所有可编辑字段。AI 自动填写的值带雾蓝色 AI 角标；用户保存过的字段标记为人工确认。后续重新分析只能更新尚未人工确认的字段，不得覆盖用户已确认的值。用户可以主动清除某字段的人工确认状态，再允许下次分析更新它。

删除采用软删除。删除后不再计入画像或复刻来源；本阶段不提供灵感永久清理任务。删除操作需要确认，并在失败时保留当前页面状态。

### 3.3 风格说明书

达到五张有效灵感后，系统从当前有效灵感的已保存字段聚合出风格说明书。没有真实 AI 时，规则聚合根据标签、色系、廓形、关键单品、组合关系和正式程度的出现次数生成可解释草稿；相同计数按最近人工确认时间和稳定编号排序，确保相同输入得到相同结果。

说明书页面分为偏爱色系、偏爱廓形、常用组合、正式程度倾向、喜欢示例和“不喜欢”六部分。所有内容均可编辑。用户修改后的说明书作为独立的人工版本保存，后续灵感变化只产生“有新的整理建议”，不能静默覆盖人工版本。

“不喜欢”规则是硬约束。第一版规则包含禁止的颜色、风格、版型、材质、正式程度和自由文字说明。可结构化的规则在复刻候选筛选阶段直接排除衣物；自由文字规则提供给真实 AI，并在结果说明中展示，但不能代替服务器可执行的结构化检查。

### 3.4 灵感复刻

详情页在灵感记录保存后显示“用我的衣服复刻”。服务器只从当前用户、状态为 `active` 的衣物中选择；草稿、观察中、已处置、回收站和其他账号的衣物均不可进入候选。衣物必须有分类和位置，图片不是参与规则复刻的必要条件。

规则预览先根据灵感的关键单品和组合关系确定所需槽位，再按品类、色系、风格、版型、长度、材质和正式程度计算相似度，同时执行“不喜欢”结构化规则。结果必须满足“上装与下装，或一件连体/裙装”的基本结构；鞋、外套、包和配饰仅在衣柜中有合适单品时加入，不得用虚构单品补齐。

如果候选足够，页面显示一套复刻结果、所用衣物、相似之处和缺失之处，并明确标注“规则预览”或“AI 复刻”。如果候选不足，页面列出缺少的品类或特征并提供返回衣柜入口，不生成购买建议。结果保存来源灵感编号、所用衣物编号、生成方式、相似说明、缺失说明和生成时的输入快照，避免后来编辑灵感或衣物后改变历史结果含义。

## 4. 数据设计

### 4.1 Inspiration

每条灵感记录属于一个用户，并关联一个已完成的 `inspiration` 类型上传。字段包括名称、风格标签、主要色系、廓形、关键单品、组合关系、正式程度、个人备注、分析状态、分析来源、各字段人工确认状态、分析错误代码、分析尝试次数、创建时间、更新时间和软删除时间。

图片关联必须通过包含用户编号的复合外键建立。一个完成的上传最多绑定一条灵感记录，不能跨用户绑定，也不能绑定 `wardrobe-original` 或 `wear-photo` 上传。图片读取通过登录态保护的私有路由完成，不返回对象存储键或长期地址。

### 4.2 StyleProfile 与 StyleRule

每个用户最多拥有一份当前风格说明书。说明书保存聚合输入版本、生成来源、偏爱色系、偏爱廓形、常用组合、正式程度倾向、喜欢示例、人工编辑标记、生成时间和更新时间。

每条“不喜欢”规则单独保存，包含规则类型、稳定值或自由文字、是否启用、创建时间和更新时间。结构化类型只接受代码内允许的稳定值；自由文字限制长度并作为普通用户内容处理，不进入日志。

### 4.3 InspirationRecreation

每次成功复刻保存一条结果记录，包含用户、来源灵感、生成方式、相似说明、缺失说明、输入快照、创建时间和更新时间。所用衣物通过子表按展示顺序关联，并使用包含用户编号的复合外键保证租户隔离。

结果记录不等同于后续完整 `Outfit`。本阶段只承担从单张灵感产生一套可查看结果；后续搭配阶段通过明确迁移或转换服务将需要收藏、替换或穿着的结果转为完整搭配，避免现在提前引入反馈与穿着生命周期。

### 4.4 ProcessingJob

真实图片分析通过数据库任务记录执行，不依赖只存在于单个进程内存中的队列。任务保存用户、任务类型、目标灵感、输入版本、状态、尝试次数、下次可重试时间、租约到期时间、安全错误代码、创建时间和更新时间。第一版任务类型只包含灵感分析；任务最多尝试两次，对应首次调用和一次格式修复重试。

同一灵感和输入版本最多存在一个未结束的分析任务。领取任务、取得有限租约和更新尝试次数必须使用原子数据库操作；租约超时后允许安全重领。完成任务时仍需检查灵感版本和人工确认状态，过期结果只能保存为历史建议，不能覆盖较新的用户内容。

## 5. 服务边界与数据流

代码按职责分为灵感记录、风格说明书、AI Provider 和复刻四个边界。页面和路由不得直接写数据库；认证后的服务负责权限、状态转换与事务，存储适配器负责私密图片，AI Provider 只负责把受控输入转换成经过模式校验的建议。

添加灵感的数据流为：浏览器预览图片 → 创建 `inspiration` 上传 → 上传到当前存储 Provider → 服务端完成并校验图片 → 创建灵感记录并绑定上传 → 配置真实 AI 时建立分析任务 → 后台任务领取并完成分析 → 用户检查并保存字段。创建记录与绑定上传在同一事务中完成，失败时上传仍保持可恢复状态，不伪装成完整灵感。

风格说明书的数据流为：读取当前用户有效灵感 → 检查五张门槛 → 生成稳定规则草稿或调用真实 AI → 运行时模式校验 → 保存新建议 → 仅在用户尚未人工编辑时更新当前说明书；否则显示可选择采纳的新建议。

复刻的数据流为：读取来源灵感和当前说明书 → 查询当前用户可用衣物 → 执行硬规则筛选 → 规则预览直接评分组合，或把候选编号及最少文字字段发送给 AI → 校验返回编号、归属、状态和硬规则 → 保存结果快照 → 返回页面。真实 AI 无权扩大候选集合或创建衣物。

## 6. AI Provider 与无 Key 模式

Provider 接口分别提供灵感图片分析、风格说明书建议和候选衣物复刻。输入和输出均使用明确的 TypeScript 类型与 Zod 运行时模式。真实 Provider 使用通义千问的 OpenAI 兼容接口，模型名、基础地址和 API Key 只从服务端环境变量读取。

没有 API Key 时，图片分析状态显示“尚未连接 AI，可手动整理”，不生成看似来自图片的标签。风格说明书使用已保存字段的确定性聚合，复刻使用确定性候选评分，并统一标注“规则预览”。测试 Provider 只能在自动测试中启用，不得通过公开请求切换，也不得进入生产用户界面。

真实 AI 请求只发送完成任务所需的压缩图片、灵感字段、说明书规则和候选衣物的临时编号及最少描述。不得发送邮箱、邀请码、密码、会话、对象存储键、长期图片地址或用户私密备注。结构化响应校验失败时自动重试一次；第二次失败保存安全错误代码并允许用户手动重试。API Key、完整提示词输入、图片内容和模型原始响应不得写入普通日志。

## 7. 错误处理与一致性

上传、记录保存、AI 分析、风格聚合和复刻分别记录状态；重试只继续失败步骤。网络中断时说明当前已保存到哪里，并提供“重试上传”“继续手动填写”或“稍后复刻”等具体操作。

AI 不可用、超时、额度不足或格式错误时，不影响查看和编辑灵感，也不影响规则画像和规则复刻。复刻保存前再次读取候选衣物状态；在生成期间被处置、移入回收站或改为观察中的衣物必须从结果中剔除，必要时重新组合或返回候选不足。

同一灵感在两台设备编辑时采用最后一次明确保存获胜，并返回最新更新时间。分析结果携带分析开始时的记录版本；如果用户在分析期间修改了字段，分析完成后不得覆盖较新的人工内容。

## 8. 安全与隐私

所有灵感、风格说明书、规则、复刻结果和图片操作都要求登录，并在数据库查询、更新、删除和关联校验中包含当前用户编号。匿名访问、跨用户编号、未绑定上传和不匹配的上传类型统一返回不泄露存在性的响应。

图片解码必须限制文件大小、像素数量和格式，并拒绝损坏文件。私有图片响应使用 `Cache-Control: private, no-store` 和 `X-Content-Type-Options: nosniff`。错误信息和日志不得包含对象存储键、私密备注、图片二进制或 AI 密钥。

## 9. 测试与验收

领域单元测试覆盖有效灵感计数、五张门槛、稳定聚合、人工字段保护、结构化“不喜欢”规则、候选筛选、相似度排序、组合完整性和候选不足说明。

数据库和 API 集成测试覆盖迁移升级、租户复合外键、上传绑定、跨用户隔离、图片私有读取、创建编辑删除、分析版本冲突、一次格式重试、AI 不可用降级、风格说明书保存、复刻编号二次校验以及生成期间衣物状态变化。

组件测试覆盖空状态、添加入口、本地预览、上传与分析状态、两列灵感墙、详情编辑、五张进度提示、风格说明书、“不喜欢”编辑、规则预览标识、复刻结果和候选不足状态。键盘焦点、44×44 CSS 像素触控目标、减少动态效果和 320 至 480 像素响应式布局继续作为验收条件。

端到端测试覆盖“邀请码注册 → 完成首次设置 → 添加衣物 → 添加五张灵感并手动标注 → 生成并修改风格说明书 → 添加不喜欢规则 → 发起规则复刻 → 验证结果只使用当前可用衣物”。另设可控测试 Provider 验证真实 AI 路径的状态转换与响应校验，但不依赖公网或真实收费 API。

阶段结束前必须通过完整单元与集成测试、类型检查、零警告代码检查、生产构建、开发模式端到端测试和本机 HTTPS 生产模式端到端测试，并更新 README、本地启动说明和独立阶段验证文档。

## 10. 后续衔接

下一阶段在本阶段的候选筛选、AI Provider、风格说明书和复刻结果基础上增加场景与天气搭配、六至八套候选生成、规则校验与评分后保留三套、替换、换一批、收藏、喜欢或不喜欢反馈、穿着确认和穿着日志。本阶段不得提前展示不可用的后续按钮或虚构搭配数量。
